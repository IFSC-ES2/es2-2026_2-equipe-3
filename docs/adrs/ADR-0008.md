# ADR-0008: Modelagem da Entidade Aluno Desacoplada de Autenticação para Reutilização na US01

## Status

Aprovada

## Contexto

No ciclo da Sprint 2, a equipe implementa a história de usuário central do sistema: a US04 (Solicitação e Aceite de Orientação), permitindo que estudantes enviem propostas aos orientadores disponíveis no catálogo.

Entretanto, no planejamento arquitetural do projeto ([`docs/entregas/sprint-2.md`](../entregas/sprint-2.md)), o módulo de Autenticação Centralizada e Controle de Acesso (US01 com Spring Security/JWT) foi programado para uma etapa posterior, priorizando a validação rápida da proposta de valor do produto e mitigando riscos de complexidade inicial.

Diante dessa premissa, surgiu o desafio técnico de como persistir os dados do estudante e associá-los à solicitação de orientação de forma consistente sem que o subsistema de login/senha esteja ativo:

- **Abordagem Ingênua:** Armazenar os dados do estudante como colunas simples de texto (`nomeAluno`, `emailAluno`) diretamente na tabela `solicitacoes_orientacao`.
- **Abordagem Estruturada (Orientada a Objetos):** Criar a entidade de domínio `Aluno` estendendo `Usuario`, persistida de forma normalizada no banco de dados com chave estrangeira `aluno_id`, mantendo os atributos de credenciais herdados temporariamente inativos até a integração com o módulo de segurança.

## Decisão

> Decidimos modelar a entidade `Aluno` como subtipo de `Usuario` (utilizando a estratégia de herança relacional `JOINED` já adotada no projeto) e relacioná-la formalmente à entidade `SolicitacaoOrientacao` via chave estrangeira (`aluno_id`), mesmo na ausência de autenticação ativa nesta etapa. As decisões sobre validações e eventos da solicitação são tratadas na [`ADR-0007`](./ADR-0007.md).

### 1. Modelo de Entidades e Persistência

- **Herança:** A classe `Aluno` estende `Usuario` (`@Entity`, `@Table(name = "alunos")`), herdando os atributos `id`, `nome`, `email`, `matricula` e `senha`. O atributo herdado `senha` permanece com valor `null` ou não utilizado durante esta versão.
- **Atributos Específicos:** A entidade adiciona o atributo `curso` (String, obrigatório).
- **Relacionamento com Solicitação:** A entidade `SolicitacaoOrientacao` possui relacionamento `@ManyToOne` com `Aluno` (coluna `aluno_id` com restrição de chave estrangeira), garantindo integridade referencial no banco de dados.

### 2. Fluxo de Criação e Reaproveitamento (Upsert Lógico)

- No endpoint `POST /api/v1/solicitacoes`, a API recebe no payload os dados cadastrais do aluno (`nome`, `email`, `curso`), conforme especificado em [`docs/contrato-dados-us04.md`](../contrato-dados-us04.md).
- Antes de persistir a solicitação, o serviço executa uma busca pelo e-mail informado:
  - **Se o aluno for inédito:** Instancia e persiste um novo registro de `Aluno`.
  - **Se o aluno já existir no banco:** Reaproveita a entidade existente sem duplicar o registro e sem sobrescrever dados prévios.
- A nova solicitação é então vinculada ao identificador (`aluno_id`) da entidade correspondente.

| **Campos soltos em `SolicitacaoOrientacao` (`nomeAluno`, `emailAluno`)** | - Não exige criar a tabela `alunos` imediatamente.<br>- Menor número de entidades JPA nesta etapa. | - Quebra o modelo orientado a objetos e o diagrama de classes.<br>- Comparação frágil de strings para checar solicitações duplicadas.<br>- **Débito técnico severo:** exigirá migração e reconciliação complexa de dados legados no futuro. | Rejeitada porque transfere um custo elevado de migração de banco para releases futuras e degrada a qualidade do design OO. |

## Consequências

### Consequências positivas

- **Eliminação de Débito Técnico de Migração (Reconciliação Futura com US01):** Quando o módulo de autenticação (US01) for integrado, a estrutura relacional de `usuarios`, `alunos` e `solicitacoes_orientacao` já estará completamente estabelecida. Bastará habilitar a gestão de senhas e a camada de segurança do Spring Security, sem necessidade de scripts de migração de dados legados ou reconciliação de cadastros dispersos.
- **Integridade Relacional e Orientação a Objetos:** Permite que a validação de solicitações duplicadas (`ValidacaoSolicitacaoDuplicadaStrategy`) opere diretamente sobre chaves estrangeiras (`aluno_id`), garantindo consistência referencial.
- **Rastreabilidade de Histórico:** O sistema viabiliza consultas e filtros unificados de todas as propostas enviadas por um mesmo aluno a partir de uma identidade única no banco.

### Consequências negativas ou riscos

- **Ausência Provisória de Verificação de Identidade:** Qualquer usuário do formulário web pode submeter uma proposta informando um e-mail válido. Esse comportamento é aceito como uma limitação temporária do MVP e está registrado na matriz de riscos operacionais (`docs/riscos.md`).
- **Necessidade de Mapeamento Inicial no Banco:** Requer a criação da tabela `alunos` no schema relacional via migração Flyway para suportar o fluxo da US04.

### Ações necessárias

- Criar a classe de entidade `Aluno.java` no pacote `br.edu.ifsc.gestao_tcc.model`.
- Criar a interface de repositório `AlunoRepository` estendendo `JpaRepository`.
- Estruturar a migração Flyway para criação da tabela `alunos` com chave estrangeira apontando para `usuarios(id)`.
- Registrar a limitação de autenticação temporária e controles compensatórios no documento de gestão de riscos (`docs/riscos.md`).

## Relação com o MVP

Esta decisão viabiliza a entrega do fluxo da US04 no cronograma da sprint com alto nível de integridade de dados e arquitetura desacoplada, blindando o sistema contra retrabalho futuro e assegurando a sustentabilidade do modelo de dados para a evolução do produto.
