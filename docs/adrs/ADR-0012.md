# ADR-0012: Backend como Resource Server OAuth2 com Validação Local de Tokens JWT do Keycloak

## Status

Proposta

## Contexto

A US01 (Autenticação e Perfis de Usuário) foi priorizada na Sprint 3, a autenticação passou a ser feita pelo Keycloak, com os papéis `ROLE_ALUNO` e `ROLE_PROFESSOR`. 

Com o login delegado ao Keycloak, falta definir como o backend (Spring Boot) reconhece o usuário em cada requisição. Até a Sprint 2, todos os endpoints de `/api/v1` eram públicos, limitação registrada como risco R06 em [`docs/riscos.md`](../riscos.md).

Os principais fatores que influenciam esta decisão são:

- **Parte do sistema afetada:** todos os endpoints REST do backend, a configuração de CORS e a suíte de testes automatizados.
- **Formato do token do Keycloak:** as roles de realm são publicadas no claim `realm_access.roles`, que o Spring Security não lê por padrão.
- **Ambiente em contêineres:** o navegador acessa o Keycloak por `http://localhost:8081`, mas o backend, dentro da rede do Docker Compose, só o alcança por `http://keycloak:8080`. O emissor (`iss`) gravado nos tokens é o endereço visto pelo navegador.
- **Pipeline de CI:** os testes automatizados são executados a cada Pull Request sem um Keycloak disponível.
- **Regra de negócio fora do token:** a permissão de gestão da turma e do calendário depende de o professor ser o responsável pela `Turma_TCC` do semestre vigente, informação que está no banco de dados da aplicação, e não no Keycloak.

## Decisão

> Decidimos configurar o backend como **Resource Server OAuth2**, usando o suporte nativo do Spring Security, para validar localmente os tokens JWT emitidos pelo realm `sigtcc` do Keycloak, pois isso retira da aplicação a responsabilidade de armazenar senhas e emitir tokens e não exige uma consulta ao Keycloak a cada requisição.

A decisão se desdobra nos seguintes pontos:

1. **Validação local do JWT.** Cada requisição a `/api/v1/**` deve trazer o token no cabeçalho `Authorization: Bearer`. O backend confere a assinatura com as chaves públicas do realm, o emissor (`iss`), a audiência (`aud` contendo `sigtcc-backend`) e a validade. Requisições sem token válido recebem `401 Unauthorized`.
2. **Emissor e endereço das chaves configurados separadamente.** A propriedade `issuer-uri` guarda o endereço visto pelo navegador, usado para validar o `iss`. A propriedade `jwk-set-uri` guarda o endereço de onde o backend busca as chaves e é sobrescrita por variável de ambiente no Docker Compose. Com isso, o backend não contata o Keycloak ao iniciar.
3. **Roles de realm convertidas em autoridades do Spring.** A classe `KeycloakRealmRoleConverter` lê `realm_access.roles` e aproveita somente as roles iniciadas por `ROLE_`, descartando as roles internas do Keycloak. As roles ficam disponíveis no `SecurityContext` para regras como `hasRole("PROFESSOR")`.
4. **API sem estado.** Não há sessão no servidor (`SessionCreationPolicy.STATELESS`) e a proteção contra CSRF é desabilitada, pois a autenticação não usa cookies.
5. **CORS centralizado.** As origens permitidas passam a ser definidas em um único ponto (`SecurityConfig`), por propriedade de configuração, substituindo as anotações `@CrossOrigin` dos controllers.
6. **Responsabilidade pela turma permanece no banco.** O token informa apenas o papel. A verificação de professor responsável pela `Turma_TCC` continua sendo feita pela aplicação.

## Alternativas consideradas

| Alternativa                                                                                    | Vantagens                                                                         | Desvantagens                                                                                                                                                   | Motivo da rejeição                                                                                                            |
| :--------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------- |
| **Login próprio no backend** (Spring Security com senha no banco e JWT emitido pela aplicação) | - Sem serviço adicional na infraestrutura.<br>- Controle total do fluxo de login. | - A equipe teria de implementar armazenamento seguro de senhas, emissão e renovação de tokens e tela de login.<br>- Maior superfície para falhas de segurança. | Rejeitada pela decisão de escopo da Sprint 3, que adotou o Keycloak para não gastar a sprint reimplementando autenticação.    |
| **Somente `issuer-uri`**, com descoberta automática das chaves                                 | - Uma única propriedade de configuração.                                          | - Dentro do contêiner, o backend não alcança `localhost:8081`.<br>- Apontar o emissor para `keycloak:8080` faria a validação do `iss` falhar.                  | Rejeitada por não funcionar no ambiente em contêineres definido na ADR-0005.                                                  |

## Consequências

### Consequências positivas

- **Nenhuma senha na aplicação:** credenciais ficam exclusivamente no Keycloak. A coluna `senha` de `usuarios`, prevista na [ADR-0008](./ADR-0008.md), deixa de ser necessária.
- **Inicialização independente:** o backend sobe mesmo com o Keycloak fora do ar, pois as chaves só são buscadas na primeira requisição com token.
- **Testes sem Keycloak:** os testes simulam um token já validado com o suporte de testes do Spring Security, mantendo o pipeline de CI sem novos serviços.
- **Mitigação do risco R06:** os endpoints deixam de ser públicos.
- **CORS em um único lugar:** elimina as origens fixas repetidas nos controllers.

### Consequências negativas ou riscos

- **Revogação não imediata:** como a validação é local, um token continua aceito até expirar, mesmo que o usuário seja desativado ou perca uma role no Keycloak. O impacto é limitado pelo tempo de vida curto do token de acesso.
- **Autorização por papel ainda não aplicada:** esta decisão exige apenas autenticação. Enquanto as regras por papel não forem adicionadas, qualquer usuário autenticado acessa todos os endpoints; o risco R06 fica mitigado apenas em parte.
- **Dependência da integração do frontend:** a partir desta mudança, o frontend recebe `401` em todas as chamadas até enviar o token do Keycloak.
- **Resposta de erro fora do contrato:** as respostas `401` e `403` geradas pelo Spring Security não seguem o formato `ErrorResponseDTO` definido nos contratos de dados.
- **Duas URLs para manter coerentes:** emissor e endereço das chaves precisam apontar para o mesmo realm em cada ambiente.

### Ações necessárias

- Adicionar o starter de Resource Server e o respectivo starter de testes ao `build.gradle`.
- Configurar `issuer-uri`, `jwk-set-uri` e `audiences` no `application.properties`, e sobrescrever o `jwk-set-uri` no `docker-compose.yml`.
- Criar `SecurityConfig` e `KeycloakRealmRoleConverter` no pacote `br.edu.ifsc.gestao_tcc.config`.
- Remover as anotações `@CrossOrigin` dos controllers.
- Criar testes automatizados para requisição sem token, com token inválido, com token válido, para o preflight de CORS e para a extração das roles.
- Definir, em tarefa própria, as regras de autorização por papel de cada endpoint.
- Padronizar o corpo das respostas `401` e `403` no formato `ErrorResponseDTO`.
- Atualizar `docs/riscos.md` e o `README.md` no fechamento da sprint.

## Relação com o MVP

A autenticação é pré-requisito das telas por perfil e do calendário de prazos (US05), que dependem de saber quem é o usuário e qual é o seu papel. Esta decisão entrega a base de identidade do backend para a US01 com o menor volume de código próprio de segurança, permitindo que a equipe concentre a Sprint 3 nas regras de negócio do MVP.
