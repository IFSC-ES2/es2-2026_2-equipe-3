# ADR-0014: Autenticação do Frontend via Direct Access Grant (Resource Owner Password Credentials) do Keycloak

## Status

Aprovada

## Contexto

A issue #130 (Tela de login integrada ao Keycloak - Frontend) exige, como critérios de aceitação:

- Formulário de login **próprio** da aplicação, com campos de e-mail e senha.
- Mensagem de erro "Credenciais inválidas" exibida **pela própria tela** quando a senha estiver incorreta.
- Redirecionamento para o painel correspondente ao papel do usuário.
- Testes de componente cobrindo login com sucesso e login com senha incorreta.

O client `sigtcc-frontend`, criado na [ADR-0011](./ADR-0011.md), foi inicialmente configurado com `standardFlowEnabled: true` (Authorization Code com PKCE), que é o fluxo recomendado pela OAuth 2.1 para SPAs públicas. Nesse fluxo, porém, o usuário é redirecionado para a página de login **hospedada pelo próprio Keycloak**: é o Keycloak quem renderiza o formulário e quem exibe a mensagem de erro de credenciais inválidas, não a aplicação React.

Isso gera um conflito direto com os critérios de aceitação da issue #130: não é possível ter "testes de componente" cobrindo "login com senha incorreta" em uma tela que não é nossa, e a UX de login deixaria de usar o visual da aplicação.

## Decisão

> Decidimos habilitar `directAccessGrantsEnabled: true` no client público `sigtcc-frontend` e implementar o login via **Direct Access Grant (Resource Owner Password Credentials - ROPC)**: o formulário React envia e-mail e senha diretamente ao endpoint `POST /realms/sigtcc/protocol/openid-connect/token` do Keycloak (`grant_type=password`), interpretando a resposta (sucesso ou `invalid_grant`) para decidir a UI.

O `standardFlowEnabled` permanece `true` no realm, preservando a possibilidade de, no futuro, migrar para Authorization Code + PKCE sem precisar reconfigurar o client do zero.

## Alternativas consideradas

| Alternativa                                                                                  | Vantagens                                                                                                                | Desvantagens                                                                                                                                    | Motivo da rejeição                                                                          |
| :------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------------------------------------------ |
| **Authorization Code + PKCE via `keycloak-js` (redirect para a tela hospedada do Keycloak)** | Fluxo recomendado pela OAuth 2.1; a aplicação nunca manipula a senha do usuário; renovação de sessão (SSO) mais robusta. | A tela de login não é controlada pela aplicação, inviabilizando testes de componente e a mensagem de erro customizada exigidos pela issue #130. | Rejeitada por conflitar diretamente com os critérios de aceitação explícitos da issue #130. |
| **Login próprio no backend (sem Keycloak)**                                                  | Controle total da UX de login.                                                                                           | Contraria a decisão já tomada na ADR-0011 de não reimplementar gestão de senhas na aplicação.                                                   | Rejeitada; fora de escopo, a ADR-0011 já decidiu usar o Keycloak.                           |

## Consequências

### Consequências positivas

- Satisfaz integralmente os critérios de aceitação da issue #130: formulário próprio, mensagem de erro customizada, redirecionamento por papel e testabilidade via componente.
- O token (`access_token`/`refresh_token`) e a expiração ficam sob controle explícito do código da aplicação (`src/auth/authService.ts`), facilitando testes automatizados sem subir um Keycloak real (mock de `fetch`).

### Consequências negativas ou riscos

- **ROPC é um fluxo marcado como legado pela OAuth 2.1** (o cliente lida diretamente com a senha do usuário, ainda que apenas para repassá-la ao Keycloak via HTTPS). Para um MVP acadêmico com usuários de teste, o risco é aceitável; para produção real, recomenda-se reavaliar a migração para Authorization Code + PKCE.
- O `access_token` é guardado em `sessionStorage` (não em cookie `httpOnly`), o que o expõe a ataques XSS caso exista alguma vulnerabilidade de injeção de script na aplicação. Mitigação: tempo de vida curto do token e ausência, até o momento, de renderização de HTML não sanitizado vindo de terceiros.
- Caso o realm seja reconfigurado manualmente (fora do `realm-import.json`) e o `directAccessGrantsEnabled` seja desativado, o login para de funcionar sem nenhum aviso explícito no frontend além do erro genérico de autenticação.

### Ações necessárias

- Manter `SIGTCC/keycloak/realm-import.json` como fonte única de verdade da configuração do client (`directAccessGrantsEnabled: true`).
- Registrar, em revisão futura de segurança, a avaliação de migração para Authorization Code + PKCE caso o sistema saia do contexto acadêmico.

## Relação com o MVP

Sem esta decisão, a US01 ficaria com o backend pronto (ADR-0011, ADR-0012) mas sem nenhuma forma de o frontend obter um token válido, mantendo o sistema inteiro inacessível (toda rota de `/api/v1/**` passou a exigir autenticação). Esta ADR destrava a integração ponta a ponta entre frontend e backend.
