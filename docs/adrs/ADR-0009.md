# ADR-0009: Adoção do Flyway para Versionamento e Migração do Banco de Dados

## Status

Aprovada

## Contexto

Nas fases iniciais do desenvolvimento do projeto (Sprint 1), utilizamos a propriedade `spring.jpa.hibernate.ddl-auto=update` para delegar ao Hibernate a responsabilidade de criar e atualizar as tabelas do banco de dados automaticamente com base nas entidades Java.

Embora essa abordagem acelere o desenvolvimento inicial, ela apresenta riscos severos à medida que o sistema cresce:
- Falta de previsibilidade sobre quais comandos DDL serão executados.
- Inconsistências estruturais entre os bancos de dados locais dos desenvolvedores.
- Ausência de um histórico versionado das alterações do banco de dados.
- Risco crítico de perda de dados em ambientes de produção (ex: o Hibernate pode remover colunas ou falhar ao renomeá-las).

Para a entrega da US04 (Solicitação de Orientação) e a preparação para o ambiente de produção, tornou-se estritamente necessário adotar uma ferramenta profissional de versionamento de banco de dados que garanta a integridade estrutural e facilite o trabalho concorrente da equipe.

## Decisão

>Decidimos utilizar o **Flyway** para gerenciar o versionamento e as migrações do banco de dados, pois ele permite um controle absoluto sobre as alterações estruturais através de scripts SQL imutáveis e versionados, garantindo consistência entre os ambientes de desenvolvimento, testes e produção.

A partir desta decisão, a propriedade `spring.jpa.hibernate.ddl-auto` passa a ser configurada obrigatoriamente como `validate`. O Hibernate servirá apenas para validar se o mapeamento das classes Java corresponde à estrutura física do banco criada pelos scripts do Flyway.

## Alternativas consideradas

| Alternativa | Vantagens | Desvantagens | Motivo da rejeição |
|---|---|---|---|
| **Hibernate (`ddl-auto=update`)** | Agilidade no desenvolvimento inicial; não exige conhecimento em SQL. | Oculta alterações destrutivas; não possui histórico; causa conflitos no controle de versão e trabalho em equipe; inaceitável para produção. | Risco inaceitável de perda de dados e falta de consistência entre os ambientes da equipe. |
| **Liquibase** | Suporta múltiplos formatos (XML, YAML, JSON, SQL); excelente para bases de dados muito complexas. | Curva de aprendizado ligeiramente maior; sintaxe XML/YAML pode ser verbosa para alterações simples. | O Flyway baseia-se puramente em SQL padrão, o que se alinha melhor com o conhecimento atual da equipe e agiliza a escrita dos scripts sem adicionar complexidade desnecessária. |

## Consequências

### Consequências positivas

- **Rastreabilidade:** Todas as alterações no banco de dados ficam registradas no histórico do repositório (Git) e na tabela `flyway_schema_history`.
- **Sincronia:** Qualquer desenvolvedor que clonar o projeto terá a garantia de rodar a mesma versão do banco de dados ao executar a aplicação.
- **Segurança em Produção:** Prevenção contra alterações acidentais na estrutura do banco que poderiam resultar em perda de dados.
- **Flexibilidade:** Possibilidade de incluir scripts de manipulação de dados (DML), como popular tabelas de domínio estáticas (ex: status, categorias).

### Consequências negativas ou riscos

- **Esforço manual:** A equipe precisará escrever comandos SQL (DDL e DML) manualmente para cada nova entidade ou alteração, em vez de depender da geração automática.
- **Imutabilidade:** Uma vez que um script de migração (ex: `V1__...sql`) é executado e o commit é integrado na `main`, ele não pode mais ser alterado. Qualquer correção exigirá a criação de um novo arquivo de migração (V2, V3, etc.).

### Ações necessárias

- Criar o script `V1__criar_tabelas_iniciais.sql` refletindo a estrutura base da US02.
- Criar o script `V2__criar_tabelas_aluno_solicitacao.sql` refletindo as novas entidades da US04.
- Atualizar o `application.properties` para `spring.jpa.hibernate.ddl-auto=validate`.
- Atualizar o `docker-compose.yml` para garantir que as variáveis de ambiente não sobrescrevam a configuração do Flyway.

## Relação com o MVP

A adoção do Flyway é fundamental para garantir a estabilidade e a confiabilidade do MVP. Como o MVP será entregue para validação em um ambiente real, garantir que o banco de dados seja provisionado de forma segura, previsível e sem perda de dados entre os deploys é um requisito não-funcional crítico para a qualidade da entrega.
