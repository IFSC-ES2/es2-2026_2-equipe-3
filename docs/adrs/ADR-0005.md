# ADR-0005: Adoção de Containers para Empacotamento e Ambiente de Desenvolvimento

## Status

Proposta

## Contexto

A equipe de engenharia precisa padronizar o ambiente de desenvolvimento, teste e implantação da aplicação. Atualmente, o sistema é composto por múltiplos serviços (API backend em Java/Spring Boot, banco de dados relacional e interface web).

Os principais fatores que influenciam esta decisão são:

- **Paridade de Ambientes:** Garantir que o comportamento da aplicação no ambiente local do desenvolvedor seja idêntico aos ambientes de homologação e produção ("funciona na minha máquina").
- **Isolamento de Serviços:** Evitar conflitos de portas, dependências e versões de software instaladas no sistema operacional host dos membros do time.
- **Facilidade de Setup / Onboarding:** Reduzir a complexidade e o tempo necessário para que novos desenvolvedores configurem as dependências do projeto (JDKs, servidores de banco de dados, variáveis de ambiente).

## Decisão

> Decidimos utilizar Docker para a containerização individual de todos os serviços do sistema e Docker Compose para a orquestração do ambiente multi-container em desenvolvimento.

## Alternativas consideradas

| Alternativa | Vantagens | Desvantagens | Motivo da rejeição |
|---|---|---|---|
| **Instalação Nativa Local (Sem Containers)** | - Zero overhead de virtualização/containerização.<br>- Execução direta e rápida no SO local. | - Alto risco de divergência de versões entre os desenvolvedores.<br>- Processo de setup manual, demorado e propenso a erros no onboarding.<br>- Dificuldade para simular serviços como bancos de dados isolados. | Rejeitada devido ao risco de divergência de ambientes e à complexidade para configurar múltiplos serviços manualmente em cada máquina. |

## Consequências

### Consequências positivas

- **Subida Rápida do Ambiente:** Qualquer desenvolvedor consegue rodar a aplicação completa executando apenas o comando docker compose up.
- **Simplificação do Deploy:** As imagens geradas no pipeline de CI/CD são prontas para produção, eliminando surpresas com dependências ausentes na nuvem.
- **Isolamento do Banco de Dados:** O banco de dados do projeto roda isolado em container com volumes persistentes configurados, sem poluir o sistema operacional local

### Consequências negativas ou riscos

- **Consumo de Memória:** Executar múltiplos containers simultaneamente exige recursos razoáveis da máquina do desenvolvedor.
- **Gerenciamento de Imagens:** Necessidade de manter as imagens base atualizadas para evitar vulnerabilidades de segurança conhecidas.

### Ações necessárias

- Criar um Dockerfile otimizado para o backend Java/Spring Boot utilizando compilação em múltiplos estágios (multi-stage build).
- Criar o arquivo docker-compose.yml mapeando as portas, redes internas e volumes de persistência (ex: dados do banco).
- Adicionar instruções no README.md do repositório explicando como subir o ambiente via Docker.

## Relação com o MVP

A containerização garante a agilidade necessária para o MVP, permitindo que o time foque na construção das funcionalidades sem perder tempo resolvendo problemas de ambiente, além de viabilizar a implantação rápida da aplicação na nuvem para os primeiros testes de validação.
